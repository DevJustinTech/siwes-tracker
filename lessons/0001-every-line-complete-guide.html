1The machine: what "running a PHP file" means

Everything else in this document only makes sense on top of one idea, so we start there: in this app, a file is a program the web server runs once per browser request. You never "launch" the app. Each URL request wakes a file up, it computes, prints HTML, and dies.

  1. Your browser sends an HTTP request: GET /siwes%20tracker/dashboard.php.
  2. Apache (XAMPP's web server) maps that URL to the folder on disk and sees the .php extension. It does not send the file to the browser — it hands it to the PHP interpreter.
  3. PHP executes the file top to bottom. Text outside <?php … ?> tags is copied verbatim into the output buffer; text inside them runs. (PHP tags — Manual)
  4. When the file finishes, Apache packages whatever was printed as the HTTP response. The browser never receives PHP source code — only HTML.

Because the script dies after every request, there is no "while the app is open" — which raises the central question of the whole course: where does state live between requests? Exactly two answers:

StoreLives inUsed here for
MySQLXAMPP's MySQL server, permanentStudents, passwords (hashed), log entries
$_SESSIONA file on the server, keyed to a browser cookie"who is logged in", flash messages, CSRF token

The session trick is the one to internalise now (full detail in part 2). When session_start() runs, PHP reads an incoming cookie (PHPSESSID=abc123…) and loads the server-side file sess_abc123… into $_SESSION. At the end of the request, whatever you put into $_SESSION is saved back. So $_SESSION['student_id'] = 5 in login.php and reading it in dashboard.php isn't memory — it's a message passed through the disk between two separate runs.

Two consequences that explain most of the code you'll see: (1) every page re-does its setup from zero — that's why every file starts with require_once __DIR__ . '/helpers.php';; (2) sending the user somewhere means telling their browser to start a new request — header('Location: …') then exit — which is why redirect() can only be called before any HTML is printed: headers ship out at the start of the response, before the body.
Hands-on checkpoint: in XAMPP with the app open, press F12 → Network tab, log out via the sidebar. You should see logout.php return status 302 with an empty response body, then an automatic second request login.php (200). That 302 is redirect() in the wild.

2config.php — the foundation, line by line

Every page in the app eventually loads config.php (via helpers.php). Its 31 lines do four jobs: declare strict typing, publish settings as constants, start the session safely, and fix the clock. Here it is whole, then dissected.

<?php
declare(strict_types=1);

define('DB_HOST', '127.0.0.1');
define('DB_NAME', 'siwes_tracker');
define('DB_USER', 'root');
define('DB_PASS', '');          // XAMPP default: empty password
define('DB_PORT', 3306);

define('APP_NAME', 'SIWES Tracker');
define('APP_URL', '/siwes%20tracker');

if (session_status() === PHP_SESSION_NONE) {
    session_set_cookie_params([
        'httponly' => true,
        'samesite' => 'Lax',
    ]);
    session_start();
}

date_default_timezone_set('Africa/Lagos');

declare(strict_types=1); (line 7)

Opt this file into strict type checking: pass an int where a string parameter is declared and PHP throws instead of quietly converting. It's per-file — which is why login.php (which has no declare) behaves slightly differently from helpers.php (which does). The app's style guide is in one line, and it matches PHP The Right Way's recommendation. (Type declarations — Manual)

The seven define() lines (10–18)

define('DB_HOST', '127.0.0.1') creates a constant: an uppercase global name, DB_HOST, whose value no code can overwrite later. Constants vs variables — DB_HOST (no $) can't be reassigned mid-request; $x can. Why 127.0.0.1 and not localhost: localhost makes MySQL try a local named-pipe/socket first; the numeric IP forces a normal TCP connection — deterministic on XAMPP on Windows.

DB_PASS is empty because that's XAMPP's stock root. That's fine here — dev machine, no external access — but is exactly the kind of line a viva will point at: on a real server, never the root user, never an empty password, never the credentials in the repo.

Dead code find: APP_URL (line 18) is defined but used nowhere — grep the app and you'll only ever see APP_NAME. It's a leftover; every link in the app is relative (href="logs.php"), which is why moving the folder doesn't break anything. Knowing your own files well enough to call out their vestigial bits is viva gold.

The session block (21–27)

Read it inside-out:

  • session_status() === PHP_SESSION_NONE — "has a session not started yet?" The guard exists because config.php might run after something else already called session_start(); starting twice would throw a warning.
  • session_set_cookie_params([...]) — configures the cookie that identifies this browser's session. Two flags, both security: httponly = JavaScript in the browser cannot read the cookie, so an XSS bug can't steal the session id via script; samesite Lax = the cookie is withheld on cross-site POSTs, so another website can't silently submit a form to your app using this visitor's session. Both are defence-in-depth behind part 10's CSRF token. (Manual)
  • session_start() — must come after setting the cookie params (they're read at start time, not retroactively), and it's the line that populates $_SESSION for the whole request. This is why config.php must load before any page reads $_SESSION — and why require_once is line 1 of the chain.

date_default_timezone_set('Africa/Lagos') (line 30)

Every date() and strtotime() call in the app — today's default in the log form, the friendly day labels, the week maths — reads this. Without it PHP defaults to UTC and would show "tonight" as "tomorrow" after 11pm. One line prevents an entire class of timezone bugs.

3helpers.php — the toolbox, function by function

121 lines, 11 functions, loaded by every page. This file is the app's framework — understanding it is understanding the whole system. It begins:

<?php
declare(strict_types=1);

require_once __DIR__ . '/config.php';
require_once __DIR__ . '/partials/icons.php';

__DIR__ = the absolute path of this file's directory — so the require works no matter where the server was started from. require_once = load and run it now; if it's already loaded in this request, skip silently. The _once matters because icons.php also needs helpers, and pages require helpers directly and through the layout — without the guard, PHP would redeclare db() and fatal.

db() — the only door to MySQL (lines 12–24)

function db(): PDO
{
    static $pdo = null;
    if ($pdo === null) {
        $dsn = 'mysql:host=' . DB_HOST . ';port=' . DB_PORT . ';dbname=' . DB_NAME . ';charset=utf8mb4';
        $pdo = new PDO($dsn, DB_USER, DB_PASS, [
            PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,
            PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
            PDO::ATTR_EMULATE_PREPARES   => false,
        ]);
    }
    return $pdo;
}

Every database line in the app starts with db(). Four ideas packed into one function:

  • The static trick. A static variable inside a function survives between calls (within one request). First call: $pdo === null, build the connection. Every later call: return the same object. This is a lazy singleton — one connection per request, created only if some code actually needs the DB. logout.php never queries the DB and never pays for a connection.
  • The DSN. One string describing where to connect: driver, host, port, database, charset. charset=utf8mb4 guarantees text arrives as true UTF-8 (and, historically, disables a charset-confusion injection vector).
  • The three options. ERRMODE_EXCEPTION: a bad query throws a catchable exception instead of failing silently — the seed.php try/catch works because of this line. FETCH_ASSOC: rows come back as arrays keyed by column name — why you write $row['work_done'] everywhere. EMULATE_PREPARES => false: don't fake prepared statements by string-building in PHP — send them to MySQL's real prepare/execute protocol, which is what makes ? placeholders genuinely injection-proof. (PDO — Manual)
  • Types. The signature function db(): PDO promises a PDO object back; with strict_types in this file, a violation is fatal, not sloppy.

The whole app's DB usage is then just the same three-step dance (prepare → execute → fetch):

$stmt = db()->prepare('SELECT * FROM students WHERE email = ?');
$stmt->execute([$email]);
$student = $stmt->fetch();        // one row, or false if none

The ? marks a placeholder: SQL structure is sent to MySQL first, the user's data separately afterwards. The data can never be parsed as SQL — that's why injection is impossible here, even though $email comes straight from a form. fetch() returns the next row (array) or false; fetchAll() returns all remaining rows as an array-of-arrays; fetchColumn() returns one scalar (you'll meet it in siwes_week_number).

e() — the output-escaping one-liner (27–30)

function e(?string $value): string
{
    return htmlspecialchars((string)$value, ENT_QUOTES, 'UTF-8');
}

?string = accepts a string or null; (string) coerces (null → ""), and htmlspecialchars replaces < > & " ' with entities like &lt; (ENT_QUOTES = also single quotes). The effect: if a student types <script>alert(1)</script> into "work done", it is stored as text, and on output rendered as visible text instead of executing. This is the second great defence (XSS), and this six-letter function is why 200+ HTML lines across the app stay safe. Rule the codebase follows everywhere: data comes out of the DB dirty; it becomes HTML only through e().

Auth helpers (33–66)

function redirect(string $path): void
{
    header('Location: ' . $path);
    exit;
}

function is_logged_in(): bool
{
    return isset($_SESSION['student_id']);
}

function require_login(): void
{
    if (!is_logged_in()) {
        $_SESSION['flash_error'] = 'Please log in to continue.';
        redirect('login.php');
    }
}
  • redirect(): the part-1 lifecycle rule in code — send the 302, then exit so no stray code runs after we've told the browser to leave. Every : void return means "returns nothing".
  • is_logged_in(): the entire authentication model is one key in one array. "Logged in" = a prior request wrote student_id into this session.
  • require_login(): the gate, called as line 3 of every protected page. Note it writes $_SESSION['flash_error'] directly rather than calling flash('error', …) — same key, just skipping the helper (a small inconsistency you're allowed to notice).
function current_student(): ?array
{
    static $student = null;
    static $loaded  = false;
    if (!$loaded && is_logged_in()) {
        $stmt = db()->prepare('SELECT * FROM students WHERE id = ?');
        $stmt->execute([$_SESSION['student_id']]);
        $student = $stmt->fetch() ?: null;
        $loaded  = true;
    }
    return $student;
}

The static-cache pattern again, twice over: $loaded ensures "checked the DB" is remembered even if the result was no row (?: — the elvis — turns false from fetch into null). A page like dashboard.php calls current_student() and gets a DB hit once, even if ten places ask. The ?array return type: array or null, because in theory the session can name a student row that no longer exists (deleted account) — and layout-top.php is written to survive null (part 4).

flash() — the one-shot message system (69–78)

function flash(string $key, ?string $message = null): ?string
{
    if ($message !== null) {
        $_SESSION['flash_' . $key] = $message;
        return null;
    }
    $value = $_SESSION['flash_' . $key] ?? null;
    unset($_SESSION['flash_' . $key]);
    return $value;
}

One function, two modes — the signature gives it away: $message defaults to null. Call it with a message → write into session (set mode). Call it without → read and immediately unset() (get mode). The unset is the whole point: a flash is shown once, then gone — reload the page and the green "Entry updated." banner doesn't come back. ?? keeps get-mode safe when there's nothing set (no warning, just null). This is how a page that redirect()s — ending its own request — can still show a message in the next request: the message rode the session across the gap from part 1.

The CSRF trio (81–103) — quick pass now, full story in part 10

function csrf_token(): string          // make (once) or return the session's secret random string
{
    if (empty($_SESSION['csrf_token'])) {
        $_SESSION['csrf_token'] = bin2hex(random_bytes(32));
    }
    return $_SESSION['csrf_token'];
}

function csrf_field(): string          // hidden input to embed in every form
{
    return '<input type="hidden" name="csrf_token" value="' . e(csrf_token()) . '">';
}

function csrf_verify(): void           // on POST: compare form value vs session value
{
    $token = $_POST['csrf_token'] ?? '';
    if (!is_string($token) || !hash_equals($_SESSION['csrf_token'] ?? '', $token)) {
        http_response_code(419);
        exit('Page expired — please go back and try again.');
    }
}

random_bytes(32) is a cryptographically-secure random generator; bin2hex renders it as 64 hex characters. hash_equals compares the attacker's guess to the secret without timing side-channel (plain === on strings returns early at the first differing byte — theoretically observable). Status 419 is a non-standard "Page Expired" (popularised by Laravel) — any 4xx would do; dying immediately is the point. All three functions exist because every mutating form in the app carries the field and calls the verifier. Part 10 ties this to the actual attack.

The two date helpers (106–120)

function day_label(string $date): string
{
    return date('D d M Y', strtotime($date));
}

'2026-09-14' → strtotime parses to a timestamp (with Lagos timezone from config!) → date('D d M Y') formats → "Mon 14 Sep 2026". Every date you see rendered in the UI passes through here.

function siwes_week_number(array $student, string $date): int
{
    $stmt = db()->prepare('SELECT MIN(entry_date) FROM log_entries WHERE student_id = ?');
    $stmt->execute([$student['id']]);
    $first = $stmt->fetchColumn();
    if (!$first) return 1;
    $weeks = (int)floor((strtotime($date) - strtotime((string)$first)) / 604800);
    return max(1, $weeks + 1);
}

"Which SIWES week is this?" — the student's earliest entry is week 1; every 604,800 seconds (= 7×24×3600, a week) advances it. MIN() with no rows returns NULL → fetchColumn() gives false → week 1. max(1, …) clamps against dates before the first entry (negative weeks). One subtlety worth seeing in logs.php: this runs one extra SQL query per rendered row — a classic "N+1". Fine for one student's dozens of rows; a scaling conversation to raise if asked.

4The partials — icons, layout-top, layout-bottom

Logged-in pages don't repeat their chrome. Instead each page is a three-act sandwich:

$page_title = 'Dashboard';
$active     = 'dashboard';
require __DIR__ . '/partials/layout-top.php';   // <!doctype> … sidebar … open <main>
?>
   …page-specific HTML here…
<?php
require __DIR__ . '/partials/layout-bottom.php'; // close <main>, footer, </html>

The variable-setting lines are an implicit contract: layout-top.php reads $page_title and $active because require runs the file in the caller's variable scope — the partial sees everything defined above it, and anything it defines leaks back. It's not magic, it's just lexical scope — but it's why the partials never work if you forget to set the variables first (they defend themselves: $page_title = $page_title ?? APP_NAME;).

icons.php — a function that returns SVG

function icon(string $name, string $class = 'icon'): string
{
    $paths = [
        'home' => '<path d="M3 10.5 12 3l9 7.5"/>…',
        // 20 more entries
    ];

    $d = $paths[$name] ?? $paths['check'];
    return '<svg class="' . e($class) . '" viewBox="0 0 24 24" …>' . $d . '</svg>';
}

A lookup array of SVG fragments keyed by name; icon('trash') returns the complete <svg> string — an SVG is just XML between two tags, stroke-based paths that inherit the text colour via currentColor. string $class = 'icon' is a default parameter — call with one argument and it fills in the rest. Unknown names fall back to the check icon (??) rather than crashing. The whole icon "library" is one function and an array — no image files anywhere.

The top of the file is all preparation, and it's instructive: it re-requires helpers (harmless _once), applies ?? defaults for the contract variables, then consumes the flashes right now (flash('error') — get mode — reads-and-deletes into local variables). That's why you never see a flash function called again lower down: they were read into $flashError/$flashSuccess before the HTML started. The nav is one array: key = page name, value = [label, svg]. Then:

<?php foreach ($navItems as $key => [$label, $svg]): ?>
    <a class="sidebar__link <?= $active === $key ? 'is-active' : '' ?>"

Three constructs in three lines: foreach … as $key => [$label, $svg] — loop with key, and destructure the two-element array into named variables. $active === $key ? 5database.sql — the schema and every constraint

The app has exactly two tables. Read database.sql alongside this; every line is a decision with a reason.

CREATE DATABASE IF NOT EXISTS siwes_tracker
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;

utf8mb4 = the real UTF-8 for MySQL (the legacy utf8 charset maxes at 3 bytes per character — no emoji, some scripts). utf8mb4_unicode_ci = collation (the rule set for comparing strings); _ci is case-insensitive: 'a@x.com' = 'A@X.COM' is TRUE in comparisons. Remember this — it makes the email uniqueness below case-proof too. (CREATE TABLE — MySQL Manual)

CREATE TABLE IF NOT EXISTS students (
  id            INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  matric_no     VARCHAR(40)  NOT NULL UNIQUE,
  full_name     VARCHAR(120) NOT NULL,
  email         VARCHAR(160) NOT NULL UNIQUE,
  password_hash VARCHAR(255) NOT NULL,
  institution   VARCHAR(160) NULL,
  … (course, placement org, supervisor) …
  created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) ENGINE=InnoDB;

Line by line, the vocabulary of constraints:

  • INT UNSIGNED: whole numbers, no sign bit — negative ids impossible, positives double-range.
  • AUTO_INCREMENT PRIMARY KEY: MySQL assigns 1, 2, 3… automatically. The PK is also physically how InnoDB stores the rows (part-2 knowledge: the clustered index) and the value PDO tells you about after an insert — $pdo->lastInsertId() in seed.php.
  • NOT NULL vs NULL: institution etc. may be empty (registered later via profile); name/email can't. NULL in SQL means "absent", not "empty string" — a distinction you saw PHP-side when fetch() returned NULLs needing ?: 'Not set' on screen.
  • UNIQUE on matric and email: the database refuses a second row with the same value, full stop — even under a race where two registrations pass the PHP check (part 7). UNIQUE is an index; the refusal beats any PHP you write.
  • password_hash VARCHAR(255): a bcrypt hash ($2y$10$…) is 60 chars; 255 is room for future algorithms (argon2id). The DB must never hold a plain password — login.php can verify without ever seeing the secret because of how these hashes work (part 6).
  • TIMESTAMP DEFAULT CURRENT_TIMESTAMP / … ON UPDATE …: MySQL itself stamps rows on insert, and re-stamps on every update. Free audit columns — PHP never sets them.
  • ENGINE=InnoDB: the transactional, FK-supporting storage engine (the old MyISAM can't do constraints).
CREATE TABLE IF NOT EXISTS log_entries (
  id            INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  student_id    INT UNSIGNED NOT NULL,
  entry_date    DATE NOT NULL,
  hours_worked  DECIMAL(4,1) NOT NULL DEFAULT 8.0,
  work_done     TEXT NOT NULL,
  challenges    TEXT NULL,
  remarks       TEXT NULL,
  … timestamps …
  FOREIGN KEY (student_id) REFERENCES students(id) ON DELETE CASCADE,
  UNIQUE KEY uq_student_day (student_id, entry_date)
) ENGINE=InnoDB;
  • DECIMAL(4,1): exact fixed-point — 4 digits, 1 after the point (max 999.9, and the app caps at 24). Why not a float? Floats store approximations; 0.5 + 0.5 + … in binary can't land on exact hours. Money-and-hours values get DECIMAL. (PHP receives them as strings — hence every display casting (float).)
  • TEXT: long variable strings — no practical width for a day's narrative. (work_done is the one NOT NULL field; the rest are optional.)
  • FOREIGN KEY … REFERENCES students(id): student_id must point at a real student row — the DB, not PHP, enforces that no orphan log can exist. ON DELETE CASCADE: delete a student and MySQL deletes their entries automatically — referential integrity as policy.
  • UNIQUE KEY uq_student_day (student_id, entry_date): the pair must be unique (a student may log 2026-09-14 once; two students may each). This is the app's "one entry per day" rule's real enforcer — log_form.php's friendly check is the courtesy layer on top. A composite index also speeds up the app's most common query (WHERE student_id = …) — its leftmost column.

The logs.php search uses work_done LIKE '%term%' — and here the two halves of this course meet: a leading wildcard can't use any index (there's no sorted structure to enter at), so that search scans. At one student's scale, irrelevant; at ten thousand students', a real conversation. You now know both layers — SQL and PHP — well enough to have that conversation in a viva.

6login.php, register.php, logout.php — authentication

The shape of a page that handles its own form

login.php, register.php and profile.php all share the pattern that defines plain-PHP web apps: one file answers both halves of a conversation.

  • GET (you open the page): the if (REQUEST_METHOD === 'POST') block is skipped, the HTML renders with empty/errors-free form. The page displays.
  • POST (you hit Submit, the same file): the block at the top runs — validate, maybe write DB, maybe redirect. Only if validation fails does execution continue into the HTML, which now re-renders with errors shown and $_POST values echoed back.

That's why $_SERVER['REQUEST_METHOD'] gates everything, and why form fields print value="<?= e($_POST['email'] ?? '') ?>" — on failed submit, your typing is restored (escaped, as always, because a POST value is user data). login.php even uses it before the POST block exists, as its display state.

login.php, top half (lines 1–31)

require_once __DIR__ . '/helpers.php';

if (is_logged_in()) { redirect('dashboard.php'); }

$error = '';
if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    csrf_verify();
    $email    = trim($_POST['email'] ?? '');
    $password = $_POST['password'] ?? '';

    if ($email === '' || $password === '') {
        $error = 'Please enter both email and password.';
    } else {
        $stmt = db()->prepare('SELECT * FROM students WHERE email = ?');
        $stmt->execute([$email]);
        $student = $stmt->fetch();

        if ($student && password_verify($password, $student['password_hash'])) {
            session_regenerate_id(true);
            $_SESSION['student_id'] = (int)$student['id'];
            $_SESSION['student_name'] = $student['full_name'];
            redirect('dashboard.php');
        }
        $error = 'Invalid email or password.';
    }
}
  • Reverse guard: if already logged in, don't show the form — push to dashboard. (register.php copies it.)
  • trim() eats stray spaces; ?? makes a missing key null-safely default; $password deliberately not trimmed (spaces may be part of it).
  • The email lookup uses the index created by UNIQUE email — the login query is a fast const-type lookup, not a scan (nice schema↔code connection).
  • $student && password_verify(...): short-circuit — the expensive hash check only runs if the row exists. And here's the part-5 promise kept: password_verify recomputes the bcrypt hash from the typed password using the salt embedded in the stored hash (the $2y$10$N9qo8uLO… format carries algorithm, cost, salt, and digest in one string) and compares. The plain password was never in the database to read.
  • session_regenerate_id(true): at the exact moment the browser's identity upgrades from anonymous to "this student", hand it a brand-new session id (and destroy the old session file). Prevents session fixation: an attacker who planted a known session id before login can't ride it afterwards. (Manual)
  • The two $_SESSION writes are the login. student_name is convenience for the UI; student_id is the credential everything else checks. (int) cast — the session can't be tricked into holding an array.
  • One error message for both failure modes: "Invalid email or password" whether the email or the password was wrong. Telling the truth ("no such email") hands account enumerators a list of registered students. Generic-on-purpose.

Remember config.php's ERRMODE_EXCEPTION: a PDO error now throws. seed.php is the one file that catches it:

try {
    $pdo = db();
    $pdo->exec('DELETE FROM log_entries');
    $pdo->exec('DELETE FROM students');
    …
    $stmt = $pdo->prepare('INSERT INTO students (…) VALUES (?, ?, ?, ?, ?, ?, ?, ?)');
    $stmt->execute([…, password_hash('demo1234', PASSWORD_DEFAULT), …]);
    $studentId = (int)$pdo->lastInsertId();

    $weeks = [ [ ['2026-07-06', 8.0, "Set up the dev environment…", 'Getting used to…'], … ], … ];

    $stmt = $pdo->prepare('INSERT INTO log_entries (student_id, entry_date, hours_worked, work_done, challenges)
         VALUES (?, ?, ?, ?, ?)');
    foreach ($weeks as $week) {
        foreach ($week as $day) {
            [$date, $hours, $work, $challenges] = array_pad($day, 4, null);
            $stmt->execute([$studentId, $date, $hours, $work, $challenges]);
        }
    }
    echo '<h2>✅ Demo data created</h2>';
} catch (Throwable $ex) {
    http_response_code(500);
    echo 'Seeding failed: ' . htmlspecialchars($ex->getMessage());
}
  • exec(): the simplest PDO method — run one static statement, no parameters, so no placeholders needed. Safe here because the SQL is literally fixed; elsewhere the app always prepares.
  • lastInsertId(): MySQL reports the AUTO_INCREMENT id it assigned (part 5's connection) — the FK needs it on every entry.
  • $weeks is an array of arrays of arrays: five weeks, each of five days, each day a 3- or 4-element list. The inner loop's [$date, $hours, $work, $challenges] = is list destructuring — unpack a positional array into named variables. array_pad($day, 4, null) pads short days to 4 elements so the destructuring never errors (days without challenges).
  • One prepare, 25 executes: the statement compiles once; each execute sends fresh bound data. This is the efficiency the prepare step buys.
  • catch (Throwable $ex): catch any PHP error or exception (Throwable is the root of both trees — Manual); 500 status + htmlspecialchars($ex->getMessage()) — even error text is escaped; the file itself instructs: delete it after seeding, because it's a public "re-create a demo password" button if left on a server.

SQL injection Type ' OR 1=1 -- in the login email to twist the query into returning the wrong row (or worse, ; DROP TABLE). Every query: prepare() + execute([values]) — the ? placeholder means data never enters the SQL grammar. EMULATE_PREPARES => false makes it MySQL's real engine enforcing this, not PHP string tricks. (part 3)
XSS (cross-site scripting) Store <script>fetch(evil)</script> in a log's work_done, waiting for a viewer's browser to run it. e() = htmlspecialchars on every output — the text renders as visible gibberish, never as markup. 11Viva drill — 14 questions, with model answers

Cover each answer before reading it; answer out loud first. These are the questions an examiner who opens this folder will ask.

1. Walk me through what happens when I load dashboard.php.

Apache hands the file to PHP. Line 1–2: require_once helpers.php → runs config.php (constants, session_start() loads my session; $_SESSION['student_id'] proves I'm logged in) and icons.php. require_login() checks the session; passes. current_student() (cached) runs a PK lookup. Three more queries: the aggregate stats row, the last 10 dates, the 5 recent entries. PHP then interleaves computed values and e()-escaped data with HTML as it prints; the partials supply the shell. Output buffer becomes the response. The file, and all its memory, cease to exist.

2. Prepared statements — what are they and why every query here uses one?

SQL structure and user values travel separately: prepare() sends the grammar with ?s (MySQL parses it immediately), execute() sends values typed as data. Values can never re-enter the parse, so injection is structurally impossible — which beats any escape routine as a strategy. db() sets EMULATE_PREPARES=false so it's MySQL doing this, not PHP faking it with quotes.

3. Where is the CSRF token stored, and what proves it?

Session (server side, in a file keyed to the cookie) and inside each form as a hidden field (browser side). On POST, csrf_verify() compares form value vs session value with hash_equals() (constant-time). Only this browser knows both halves — an external site's form can carry the user's automatic cookie but can never read the session's token, so its submission dies with 419.

4. Password security: what's in the database, and what happens at login?

60-character bcrypt strings: algorithm tag + cost (2^10 work) + random 16-byte salt + digest, all in one value, one row — register.php's password_hash(). At login password_verify() re-runs bcrypt on the typed password with the stored salt and compares digests — the plain password is never stored or recovered. The salt makes identical passwords hash differently; the cost makes brute force ~0.1s/guess instead of ~0.000001s.

5. One entry per day — where is it enforced and why twice?

Database: UNIQUE KEY uq_student_day (student_id, entry_date) — absolute, race-proof. PHP: the SELECT … id <> ? check in log_form.php — friendly: turns a constraint error into a per-field message naming the date. The PHP check can't be the security boundary (TOCTOU race between its SELECT and INSERT); the constraint can. Belt and braces.

6. What's $_SESSION technically?

An ordinary array in the running script, populated at session_start() from a server file (sess_<id>) whose name came from the visitor's PHPSESSID cookie, and re-written at script end. It's a disk-backed mailbox between two separate executions of two different files — which is how logout can affect the next request's is_logged_in(), and how flash messages survive redirects.

7. How does one file serve both "new entry" and "edit entry"?

Presence of ?id=: $id = (int)$_GET['id'] ?? 0;; $id > 0 triggers a scoped SELECT whose row supplies form defaults (with ?? fallbacks for create mode); the title, submit-label, and POST branch (UPDATE vs INSERT) all check $id. A single CRUD form, two modes.

8. What is the Post/Redirect/Get pattern and where does the app use it?

Every successful POST (login, register, save, delete) ends with redirect() to a GET page instead of rendering — so refresh resubmits nothing, and the confirmation is a session-riding flash() consumed by layout-top.php. Failed validations deliberately don't redirect — they re-render the form with $errors and echoed values.

9. Why can <?= be everywhere but header() only at file tops?

<?= appends to the response body; header() appends to the response head, and the head must already be sent before the first body byte. PHP buffers headers until output starts — redirect() calls therefore must precede any HTML in a file (the reason the app's PHP logic sits above its markup).

10. What's an N+1 query and where does it lurk here?

One query for the rows, then one more per row. siwes_week_number() runs SELECT MIN(entry_date) … per rendered row on dashboard and logs — the recent list costs 1 + 5. The fix: compute MIN once before the loop (or cache). Harmless at this scale, the first fix at scale.

11. Why are there only two tables, and how does the app draw "a student's entries"?

Relational: log_entries.student_id is the FK; "their" = WHERE student_id = ?, bound from $_SESSION. Normalisation: names once, not per-entry. The composite UNIQUE both enforces the daily rule and indexes the dominant query path. The FK guarantees integrity from the other direction.

12. Why does fetch() sometimes mean false, sometimes a row with nulls?

Zero rows → false (that's why if (!$student) works after login). Rows exist but nullable columns empty → array with null values. Hence the app's two idioms: ?: null/if (!$entry) for row existence, and ?? 'default'/?: 'Not set' for empty fields. Two different absences.

13. Where could this app improve if it went to production?

A good viva answer is layered: real DB user with password, no root; require login-over-HTTPS (secure cookie flag); rate-limit the login form (bcrypt cost per attempt is partial help); replace the register.php "email exists" message with a neutral one (it currently confirms accounts — a deliberate trade-off for this audience); fix seed.php deletion; the N+1; logging of PDO exceptions instead of raw 500s; a CSRF edge-case: tokens never rotate (acceptable, but worth naming). Showing you know the app's compromises and their reasons is the point.

14. Why PHP and not a framework?

Deliberate for this project: every mechanism visible. A framework would hide exactly the things examined here — sessions in middleware, CSRF in a template tag, PDO in an ORM. No Composer means require_once is the dependency system, and the 121-line helpers.php is a 20,000-word explanation of what Laravel does with Artisan make:auth.
