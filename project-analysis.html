SIWES Tracker — What Every File Does

A student log-book app built twice: once as a server-rendered PHP site, and once as a REST API in FastAPI. Both share one MySQL database, so an entry logged in either appears in both. This is a file-by-file tour of how the whole thing fits together.

The shape of the projectoverview

The repo splits into five layers. The PHP app is a classic page-per-file site; the FastAPI backend mirrors its features as JSON endpoints. They never talk to each other directly — they meet at the database.

PHP web approot *.php

Server-rendered pages: dashboard.php, logs.php, log_form.php and friends. Each page handles its own GET/POST and prints HTML through shared partials.

FastAPI backendbackend/app/

The same features as REST endpoints with JWT auth. Routers live in router_auth.py, router_logs.py, router_misc.py.

Shared databasedatabase.sql

One schema, two consumers. Two tables — students and log_entries — and a unique key that enforces one entry per student per week.

Frontend assetsassets/

One hand-written stylesheet (light + dark themes) and one small vanilla JS file for the theme toggle, mobile sidebar and password eye.

Plumbingpartials/, config, seed

The layout shell, the SVG icon set, DB credentials, helpers and a demo-data seeder round out the PHP side.

Verificationbackend/smoke_test.py

An end-to-end test that drives register → login → CRUD → stats against an in-memory database, plus the two README files.

A request through the PHP apphow it runs

Every protected page walks the same path. Take logs.php as the example:

  1. Boot. The page requires helpers.php, which loads config.php (credentials, session start) and partials/icons.php (the icon set).
  2. Guard. require_login() checks the session; an anonymous visitor is bounced to login.php with a flash message.
  3. Handle. For POST requests, csrf_verify() checks the token before any input is trusted.
  4. Query. Data comes back through PDO prepared statements scoped to $_SESSION['student_id'] — a student can only ever see their own rows.
  5. Render. partials/layout-top.php opens the shell (sidebar, topbar, flash alerts), the page prints its section, partials/layout-bottom.php closes it and pulls in assets/js/app.js.

Database & configuration3 files

database.sql
54 lines · schema
The shared contract

Creates the siwes_tracker database and its two tables. students holds accounts (matric number, name, hashed password, institution, placement details); log_entries holds weekly logs (week start, days, hours, work done, challenges, supervisor remarks).

Two details carry weight: uq_student_week — a unique key on (student_id, week_start) that makes duplicate weekly entries impossible even if the app code had a bug — and ON DELETE CASCADE, so deleting a student removes their entries cleanly.

config.php
30 lines · PHP settings
One place to change everything

Defines the DB credentials (XAMPP defaults: root, empty password), the app name and URL, the timezone, and starts the session with hardened cookie flags (httponly, samesite=Lax). Every other PHP file reaches settings through here.

backend/.env.example
12 lines · Python settings template
The FastAPI twin of config.php

Documents the environment variables the Python backend reads: the same database fields, plus JWT_SECRET and token lifetime. Copy to .env and adjust; nothing secret is committed.

PHP core — the plumbing every page leans on4 files

helpers.php
130 lines · function library
The app's toolkit

The most-reached file in the project. It provides db() (a lazily-created, shared PDO connection), e() (HTML-escaping used on every piece of printed data), redirect(), and the auth trio: is_logged_in(), require_login(), current_student().

It also owns the security primitives — one-shot flash() messages, csrf_token() / csrf_field() / csrf_verify() — and the domain date logic: week_start_of() snaps any date to its Monday, week_label() formats a friendly range, and siwes_week_number() counts which week of the placement an entry belongs to.

partials/icons.php
37 lines · icon set
One function, seventeen icons

Maps names like 'home' or 'trash' to inline SVG markup (Lucide-style strokes, 24×24). Inlining keeps the UI free of emoji icons and an icon-font dependency, and lets CSS color the icons with currentColor.

partials/layout-top.php
88 lines · page shell (opens)
Everything around the content

Prints the <head>, the dark-teal sidebar (brand, nav with the active page highlighted, user avatar, logout), and the topbar with the menu and theme-toggle buttons. It then opens the content area and renders any pending flash messages as success/error alerts. Pages set $page_title and $active before including it.

partials/layout-bottom.php
10 lines · page shell (closes)
The other half of the shell

Closes the content and main containers, prints the footer, and loads assets/js/app.js. Together with layout-top.php it guarantees every page has an identical frame.

PHP auth pages3 files

login.php
83 lines · standalone page
The front door

A standalone page (no sidebar — it uses its own centered card layout). On POST it verifies the CSRF token, looks the email up, and checks the password with password_verify(). On success it regenerates the session ID (a session-fixation defence) and stores the student's ID in the session. The same generic error covers wrong email and wrong password, so the form can't be used to discover which accounts exist.

register.php
137 lines · standalone page
Account creation with field-level validation

Validates each field individually and re-renders the form with inline errors and the submitted values preserved: required fields, email format, an 8-character password minimum, matching confirmation, then a database check that neither the email nor matric number is already taken (each gets its own message). Passwords are stored with password_hash() — bcrypt — which is exactly what the Python backend expects, so accounts work in both apps.

logout.php
6 lines · action
The exit

Clears the $_SESSION array, destroys the session, redirects to the login page. Deliberately the smallest file in the project.

PHP feature pages — the CRUD4 files

dashboard.php
177 lines · read
The landing page after login

Runs one aggregate query for the stat cards (weeks logged, total hours, days worked, week span), a second for the last 8 weeks' hours, and a third for the 5 most recent entries. The chart is pure CSS — each bar is a <div> whose height is a percentage — so it needs no chart library and adapts to the theme for free. A placement card shows the student's organisation and supervisor, and an empty state invites the first entry.

logs.php
90 lines · read + search
The log book itself

Lists every entry, newest week first, in a table with days, hours, a truncated work-done summary, challenges and edit/delete actions. The search box filters by keyword against work done, challenges and week dates using a parameterised LIKE query — the % wildcards live in PHP, not in user-supplied SQL.

log_form.php
146 lines · create + update
One form, two jobs

The heart of the CRUD. Opened without an ID it creates; opened as log_form.php?id=5 it loads that entry and updates it. Validation mirrors the database: the week date is snapped to Monday, days must be 1–7, hours 0.5–168, work-done is required, and a duplicate-week check (excluding the entry being edited) runs before insert — so the user gets a friendly "you already logged this week" instead of a raw SQL error.

log_delete.php
53 lines · delete
Deletion with a speed bump

GET shows a confirmation page summarising the entry (week, days, hours, a quote of the work done); POST with a valid CSRF token performs the DELETE. Both queries are scoped to the logged-in student's ID, so one student can never delete another's entry even by guessing IDs.

PHP profile & utilities3 files

profile.php
157 lines · read + update
Two forms, one page

Dispatches on a hidden action field: details updates name, institution, course and placement info; password verifies the current password before storing the new hash. The matric number is shown read-only (it's the academic identifier, not a preference). Field-level errors render inline, same pattern as the register page.

seed.php
63 lines · demo utility
Sample data for demos

Wipes the tables and creates one demo student (demo@siwes.test / demo1234) with eight realistic weeks of entries, so the dashboard chart has something to show. Designed to be run once and deleted — it resets all data.

router.php
33 lines · dev-server router
Only needed without Apache

Lets the app run on PHP's built-in server (php -S localhost:8000 router.php): it serves real files directly, sends the root to the dashboard or login depending on session state, and maps /dashboard to dashboard.php. Irrelevant under XAMPP, where Apache's directory routing does this.

Frontend assets2 files

assets/css/style.css
693 lines · design system
The entire visual identity

The largest file in the project, and the only styling — no framework. It opens with two token blocks: a light palette on :root (warm-teal text on off-white, cyan primary, colour-coded stat accents) and a dark palette on :root[data-theme="dark"] that redefines only the tokens. Every component — sidebar, cards, stat tiles, tables, forms, alerts, the auth pages, the CSS bar chart — is then styled through those tokens, which is why the theme toggle is a one-attribute switch.

It also handles the responsive shell: below 860px the sidebar becomes an off-canvas drawer behind a backdrop, form grids collapse to one column, and a prefers-reduced-motion block stills the animations.

assets/js/app.js
71 lines · vanilla JS
Three behaviours, no libraries

The theme toggle (reads/writes localStorage and swaps the moon/sun icon), the mobile sidebar (hamburger opens, backdrop click and Escape close, aria-expanded kept honest), and the password show/hide eye on the auth forms. All three degrade gracefully — with JS off, the site still works, it just stays in light mode.

FastAPI backend — structure4 files

The Python backend mirrors the PHP app's features as JSON endpoints. Layout is conventional FastAPI: settings, session, security, models, schemas, then routers.

backend/app/core/config.py
33 lines · settings
Typed configuration

A Pydantic Settings class reading .env: the same DB fields as config.php (same defaults), plus JWT_SECRET, algorithm and token lifetime. Cached via @lru_cache so the file is read once per process.

backend/app/core/database.py
35 lines · DB session
The SQLAlchemy engine

Builds the mysql+pymysql engine from settings (with pool_pre_ping so dropped connections self-heal) and a sessionmaker. get_db() yields a session per request and closes it in finally — the FastAPI idiom for dependency-injected transactions.

backend/app/core/security.py
39 lines · hashing + JWT
Where passwords and tokens meet

Bcrypt hashing via passlib — deliberately the same algorithm as PHP's password_hash(), which is what makes cross-app logins possible. Also issues JWTs (student ID as subject, 24-hour expiry) and decodes them, returning None on any invalid or expired token.

backend/app/models.py
56 lines · ORM models
Python's view of the shared tables

Student and LogEntry mapped exactly onto the existing students and log_entries tables — column types match database.sql (including the DECIMAL(5,1) hours). There is no create_all() anywhere: the API treats the PHP app's schema as the source of truth, which is why both apps can write to the same data.

backend/app/schemas.py
106 lines · request/response contracts
Validation at the boundary

The Pydantic models each endpoint accepts and returns: StudentCreate (8-char password minimum, valid email), LogEntryCreate with its snap_to_monday validator — the direct equivalent of the PHP week_start_of() — plus separate read models that keep the password hash out of responses, and the dashboard stat/chart models.

backend/app/dependencies.py
26 lines · auth gate
Who is asking?

Extracts the Bearer token, decodes it, and loads the matching Student — or raises a 401. Any endpoint that takes student = Depends(get_current_student) is protected; the student object it returns is also the scoping rule for every query.

FastAPI backend — the routers3 files

backend/app/router_auth.py
65 lines · 3 routes
Register, login, me

POST /auth/register upper-cases the matric number, checks email/matric uniqueness with distinct 409 messages, hashes and stores. POST /auth/login uses FastAPI's OAuth2 form so the Swagger "Authorize" button works natively, and returns the same generic error for unknown email and wrong password — mirroring login.php's anti-enumeration stance. GET /auth/me returns the authenticated student.

POST /auth/register POST /auth/login GET /auth/me

backend/app/router_logs.py
147 lines · 6 routes
The full CRUD surface

List with optional keyword search, fetch one by ID, fetch by week (any day snaps to Monday), create, partial-update via PUT with exclude_unset semantics, delete. A shared helper performs the duplicate-week check and raises 409, matching the unique key in database.sql. Every query filters on the authenticated student's ID — the same ownership scoping the PHP app enforces.

GET /logs GET /logs/week/{date} GET /logs/{id} POST /logs PUT /logs/{id} DELETE /logs/{id}

backend/app/router_misc.py
93 lines · 5 routes
Dashboard and profile

One aggregate query powers /dashboard/stats (count, summed hours and days, week span); /dashboard/chart returns the last N weeks for the frontend chart. Profile endpoints read, patch and handle password changes (current password verified first). Errors use proper status codes: 400 for a wrong current password, 404 for missing entries.

GET /dashboard/stats GET /dashboard/chart GET /profile PATCH /profile POST /profile/password

The two apps, side by sideparity

Same database, same rules, two runtimes. Each security or domain rule in the PHP app has a direct counterpart in the API:

  1. Weeks snap to Monday — week_start_of() in helpers.php ↔ the snap_to_monday validator in schemas.py.
  2. One entry per week — the unique key in database.sql, pre-checked in log_form.php ↔ pre-checked with a 409 in router_logs.py.
  3. Ownership scoping — every query carries student_id from the session ↔ from the JWT subject.
  4. Passwords — password_hash() ↔ bcrypt via passlib: the same hashes, so either app can verify them.
  5. Request tampering — CSRF tokens on forms ↔ JWT signatures on API calls.
  6. Quiet errors — one generic login failure in both, no account enumeration.
If you only remember one thing: the app is deliberately boring architecture done carefully — page-per-file PHP with prepared statements and escaped output, a REST twin with JWT, and one database whose unique key enforces the one rule that matters most.
